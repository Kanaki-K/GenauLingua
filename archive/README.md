# Архив: след правок, а не инструментарий

Здесь лежит то, что **однажды сработало и больше не запускается**. Файлы
остаются в репозитории нарочно: по ним видно, откуда взялось каждое
решение в словарной базе и почему она выглядит так, а не иначе. Удалить
их значило бы потерять провенанс 14 888 правок.

**Ничего отсюда не зовут ни бот, ни тесты, ни приёмка.** Проверено
машинно перед переносом: ни одного импорта из живого кода, ни одной
ссылки как на команду к запуску в рабочих документах.

---

## Зачем это разложили

До 13 октября 2026 всё лежало в одном каталоге `app/scripts`, и он
выглядел так:

```
живого кода в app/           20 361 строка
в app/scripts               101 260 строк     — впятеро больше
из них применённых правок    79 000 строк     — 79%
```

Отличить рабочий инструмент от применённой однажды правки было нельзя
ничем, кроме чтения каждого файла. Хуже того: `.gitignore` игнорировал
`app/scripts/*` целиком, а нужное перечислял исключениями — таких строк
накопилось **318 при 483 строках во всём файле**. То есть код
отслеживался списком, а не правилом.

У этого было два следствия, и оба успели сработать.

**Новый инструмент исчезал молча.** Забыл дописать строку в `.gitignore`
— и приёмка, которую ты только что написал и прогнал, в коммит не попала.
За один час работы это случилось дважды. Ровно так же когда-то пропал
`audit_admin`: приёмка админ-панели лежала в репозитории, не упомянутая
ни в одном документе и не включённая ни в один порядок прогона.

**Переворот правила вскрыл восемь файлов, которых git не видел вообще** —
включая `app/scripts/__init__.py`, без которого на свежей копии не
работает ни один запуск `python -m app.scripts.*`.

## Что где

### `wordbase_review/` — 219 файлов, ~79 000 строк

Применённые правки словарной базы: три прохода вычитки, 14 888 правок.
Каждый файл несёт в заголовке разбор того, что именно правилось и почему
— это и есть ценность. Журнал решений — `REVIEW_LEDGER.md` в корне.

Отнесены сюда по трём условиям разом: не упомянуты ни в одном рабочем
документе, никем не импортируются, и по природе своей — разовая правка
данных (`fix_*`). Повторяемые правки (`fix_turkish_i`,
`fix_uk_apostrophe`, `fix_examples`, `fix_example_equals_word`) остались
в `app/scripts`: они нужны после каждого прогона переводов.

### `superseded/` — 7 файлов

Вытесненное и опасное. Эти файлы **не были отслеживаемы вообще** —
`.gitignore` их скрывал, поэтому их никто ни разу не смотрел. Их стоит
знать поимённо, потому что соблазн «запустить проверку рейтинга» никуда
не денется:

| файл | почему вынесен |
|---|---|
| `check_leaderboard.py` | зовёт `load_dotenv()` без параметров, то есть читает `.env` — **боевой** — и соглашение `ENV_FILE` обходит. «Диагностика рейтинга» полезла бы в прод |
| `check_table.py` | то же |
| `check_full_system.py` | то же |
| `reset_user.py` | 17 строк, сбрасывает прогресс человека, и по умолчанию на ПРОДЕ. Без описания, без подтверждения, невидим для git |
| `check_integrity.py` | 387 строк проверки, которая ищет файлы не от корня и рапортует **57 ложных ошибок** («не найден `app/main.py`») с выводом «исправь перед деплоем». Ровно то, что в проекте записано как «проверка врёт чаще кода» |
| `broadcast_april.py` | разовая рассылка за апрель |
| `safe_migrate_words.py` | разовая миграция, и её описание — копия описания рассылки, то есть врёт о том, что файл делает |
| `docker-compose.prod.yml` | **третье определение прода, на которое не ссылается никто**: ни `DEPLOY.md`, ни один скрипт. Прод поднимается обычным `docker-compose.yml` (в `DEPLOY.md` команда без `-f`), и этот файл расходился с ним — не имел ни монтирования каталога, ни запуска миграций. Читатель, искавший «как устроен прод», нашёл бы здесь неправду |

Чем они вытеснены: целостность и озвучка — `state_report`, рейтинг и
учёт — `repair_accounting` вместе со сторожем в `state_report`, круг и
игры — `audit_round`, админка — `audit_admin`. Все эти читают настройки
через `app.config`, а он слушается `ENV_FILE`.

## Если понадобится что-то отсюда достать

Правки словаря писались под состояние базы на тот день. Повторный запуск
через полгода может не найти ряда, который уже поправлен иначе. Поэтому:
читать — да, запускать — только разобравшись, что ряды на месте.
